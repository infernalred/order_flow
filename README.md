# OrderFlow

OrderFlow — учебная event-driven платформа оформления, оплаты, резервирования и доставки заказов для небольшого маркетплейса.

Главная цель проекта — научить разработчика, знакомого с C#, самостоятельно писать и объяснять идиоматичный Go. Сначала идут упражнения по языку и HTTP API в памяти, затем модульный монолит с PostgreSQL и завершённым checkout. Kafka и Saga добавляют практику надёжной обработки сообщений; выделение сервисов, полный observability stack и Kubernetes образуют продвинутый трек. Опыт ASP.NET и распределённых систем не является обязательным.

> Event-driven здесь не означает Event Sourcing. Актуальное состояние хранится в PostgreSQL, а события используются для надёжного взаимодействия компонентов.

## Чему должен научить проект

- семантике значений, указателям, slices/maps, zero value, методам, интерфейсам, packages и базовым generics;
- идиоматичному Go: композиции, маленьким интерфейсам, явной обработке ошибок и `context.Context`;
- построению HTTP API и, на позднем этапе, gRPC API;
- работе с PostgreSQL, транзакциями, `pgx/v5`, `sqlc` и миграциями;
- конкурентной обработке без бесконтрольного создания goroutine;
- надёжной доставке сообщений через Transactional Outbox и Inbox;
- идемпотентности HTTP-запросов, consumers и внешних операций;
- оркестрации Saga, компенсациям, retry и DLQ;
- graceful shutdown, тестированию с race detector и профилированию;
- OpenTelemetry, Prometheus, Grafana, Tempo и Loki;
- контейнеризации, Kubernetes, Helm и CI/CD.

## Возможности системы

Покупатель сможет:

- просматривать каталог;
- создавать и оплачивать заказ;
- получать рассчитанную итоговую стоимость;
- отслеживать состояние и историю заказа;
- отменять заказ;
- получать уведомления.

Администратор сможет:

- управлять товарами и остатками;
- просматривать заказы и состояние workflow;
- просматривать DLQ и повторно запускать неудачные операции.

Система должна корректно переживать повторные HTTP-запросы и сообщения Kafka, падение consumer, недоступность Kafka, тайм-аут платёжного провайдера, конкуренцию за последний товар, рестарт процесса, SIGTERM во время обработки и нарушение порядка доставки событий.

## Архитектурный подход

Развитие проекта намеренно разбито на этапы:

1. Модульный монолит с модулями `catalog`, `orders`, `inventory`, `payments`, `delivery` и `notifications`.
2. Transactional Outbox, Kafka и первый отдельный consumer — Notification Worker.
3. Checkout Workflow, управляющий Saga.
4. Последовательное выделение Inventory, Payment и Delivery в отдельные сервисы.
5. Развёртывание компонентов в Kubernetes.

На первом этапе модули работают в одном процессе и используют одну PostgreSQL с отдельными схемами. Межмодульное взаимодействие выполняется синхронно через Go-интерфейсы. Это позволяет сначала освоить язык и транзакции, не пряча ошибки проектирования за сетевыми границами.

Подробности: [архитектура и надёжность](docs/architecture.md).

## Основной сценарий

```text
POST /v1/orders
        │
        ▼
Order + OrderCreated сохранены в PostgreSQL одной транзакцией
        │
        ▼
Outbox Relay публикует событие в Kafka
        │
        ▼
Checkout Workflow запускает Saga
        │
        ├── ReserveStock
        ├── AuthorizePayment
        ├── CreateDelivery (предварительная заявка)
        ├── CapturePayment
        ├── CommitStock
        └── OrderConfirmed → NotificationRequested
```

Компенсации:

- недостаточно товара: заказ получает статус `REJECTED`;
- авторизация оплаты отклонена: резерв освобождается, заказ отклоняется;
- доставка не создана до capture: авторизация отменяется, резерв освобождается, заказ отклоняется;
- capture окончательно отклонён: предварительная доставка отменяется, оставшаяся авторизация и резерв освобождаются;
- после capture резерв истёк и CommitStock отклонён: выполняются refund и отмена доставки, заказ отклоняется;
- CommitStock уже выполнен: подтверждение заказа восстанавливается повтором; временный сбой не превращает оплаченный заказ в отклонённый.

Timeout означает неопределённый результат и требует сверки. Пользовательская отмена разрешена только до запуска capture; гонка отмены и capture разрешается состоянием workflow. Возврат после подтверждения/отгрузки не входит в первую версию. Подробные переходы и поздние результаты описаны в архитектуре.

Бизнес-статус заказа отделён от технического статуса Saga. Например, заказ может оставаться `PENDING`, пока workflow проходит шаги `STOCK_PENDING`, `PAYMENT_PENDING` и `DELIVERY_PENDING`.

## Модули

| Модуль | Ответственность |
| --- | --- |
| Catalog | Товары, названия, описание, актуальная цена, активность |
| Orders | Состав и стоимость заказа, статус, история, отмена |
| Inventory | Остатки, резервирование, освобождение и expiration |
| Payments | Sandbox-платежи, authorize, capture, cancel authorization, refund и управляемые сбои |
| Delivery | Sandbox предварительных доставок, адрес, временное окно, статусы и отмена |
| Checkout Workflow | Состояние Saga, retry и компенсации |
| Notifications | Уведомления по событиям заказа |

Деньги хранятся только в минимальных единицах валюты (`199900` = `1 999,00 RUB`). `float32` и `float64` для денег не используются. Money также хранит валюту и проверяет переполнение и допустимые количества. Название и цена товара сохраняются в заказе как snapshot.

## Планируемый HTTP API

```text
POST   /v1/admin/products
PATCH  /v1/admin/products/{productId}
GET    /v1/products
GET    /v1/products/{productId}

PUT    /v1/admin/stock/{productId}
GET    /v1/admin/stock/{productId}

POST   /v1/orders
GET    /v1/orders/{orderId}
GET    /v1/orders
POST   /v1/orders/{orderId}/cancel

GET    /v1/admin/workflows/{orderId}
GET    /v1/admin/outbox
GET    /v1/admin/dead-letters
POST   /v1/admin/dead-letters/{id}/retry
POST   /v1/admin/dead-letters/{id}/discard
```

`POST /v1/orders` требует заголовок `Idempotency-Key` в области клиента и операции. До Saga endpoint создаёт ресурс заказа и возвращает `201 Created`; на этапе 3B checkout выполняется синхронно с сохранением прогресса. После перехода на асинхронный контракт принятия checkout используется `202 Accepted` и ссылка на заказ. Это выбранный контракт проекта: асинхронная обработка сама по себе не запрещает `201` для уже созданного ресурса.

Чтение, список и отмена заказов проверяют владельца; административные endpoints требуют роли. Для обучения достаточно минимальной аутентификации с тестовыми identities. Списки имеют пагинацию, HTTP body — лимит размера; PATCH отличает отсутствие значения от явного изменения на ноль.

## Путь из .NET в Go

Обязательная последовательность обучения находится в [roadmap](docs/roadmap.md):

1. **A — язык:** значения и указатели, slices, maps, interfaces, typed nil, ошибки, defer, packages/modules и generics.
2. **B — HTTP в памяти:** стандартная библиотека, JSON, middleware, `httptest`, fakes, базовая отмена и владение ресурсами.
3. **0–1 — приложение и PostgreSQL:** lifecycle, Catalog/Orders, SQL, транзакции, доступ и идемпотентность.
4. **C — concurrency:** goroutine в сравнении с Task/async-await, mutex/channels, bounded workers, отмена и ожидание завершения.
5. **2–3B — законченный монолит:** Inventory, Payments, Delivery и синхронный восстанавливаемый checkout.
6. **4–6 — сообщения:** Outbox, Kafka, Inbox, DLQ и Saga с теми же бизнес-инвариантами.
7. **7–10 — продвинутый трек:** отдельные сервисы, распределённая диагностика, Kubernetes и измеримая оптимизация.

Каждая тема проходит через объяснение, упражнение, проектную задачу и самостоятельное изменение с тестом. DoD проверяет и поведение системы, и понимание ученика. Первые метрики и знакомство с профилированием появляются на монолите, до полного observability stack.

Несколько правил для проекта:

- не создавать интерфейс для каждого типа; интерфейс объявляет потребитель и только для реально нужных методов;
- не имитировать исключения: ошибки возвращаются явно, оборачиваются через `%w` и классифицируются через `errors.Is`/`errors.As`;
- не строить DI-контейнер на старте: зависимости явно собираются в `main`;
- не добавлять goroutine без понятного владельца, отмены через context и ожидания завершения;
- не прятать SQL за универсальным repository/framework слоем;
- начинать с стандартной библиотеки и добавлять зависимости для конкретной задачи;
- принимать `context.Context` первым аргументом там, где операция требует отмены/deadline; не добавлять его к чистым расчётам и не хранить в долгоживущих структурах;
- предпочитать table-driven tests.

Пример небольшого интерфейса со стороны потребителя:

```go
type ProductReader interface {
	GetProducts(ctx context.Context, ids []uuid.UUID) ([]Product, error)
}
```

## Проверки качества

Минимальный набор команд для каждого этапа:

```bash
go test ./...
go test -race ./...
go test -shuffle=on ./...
```

Сейчас `make test` запускает обычные тесты, а `make lint` — `go vet`; расширение lint и CI запланировано в этапе 0. Race detector проверяет выполненные пути Go-кода, но не заменяет тесты транзакционных гонок, deadlock, отмены и утечек goroutine.

## Roadmap

Обучение начинается с блоков A и B, затем продолжается в существующем репозитории. Выполненные задачи этапа 0 сохранены; учебные проверки проходят отдельно. Перед Kafka должен работать полный checkout монолита, включая Delivery, capture и списание резерва.

Полный порядок задач и Definition of Done: [roadmap](docs/roadmap.md). Roadmap разбит на небольшие подэтапы и оформлен как Markdown task list, поэтому выполненные задачи можно отмечать галочками прямо по ходу разработки.

## Что намеренно не входит в первую версию

Elasticsearch, GraphQL, Event Sourcing, отдельная CQRS read database, Service Mesh, Kubernetes Operator, Vault, Keycloak, несколько Kafka-кластеров, распределённый кеш «для всего» и универсальная event-bus библиотека.

Эти технологии можно изучать отдельно, но они не должны мешать основной цели — освоить Go и надёжную обработку заказов.

## Текущий статус

Этап 0 реализован частично: есть Go module, конфигурация, структурированные логи, health endpoints, middleware и тесты. Завершение инфраструктуры отслеживается в roadmap. Следующий учебный шаг — пройти проверки блоков A и B, затем продолжить незакрытые задачи этапа 0. Наличие кода не означает, что соответствующая тема уже освоена.
